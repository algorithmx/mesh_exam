Architecture at a glance

The examiner is a Python inspection framework built around a canonical mesh representation. Loaders and adapters translate file formats and library objects into MeshInput; registered operations inspect that shared model and a workflow aggregates their findings into an InspectionResult.

Evidence: mesh_loader.py:125–340, operation_registry.py:156–207, models.py:173–229, 255–321.

From file to finding

  1. Load. The loader checks the extension and selects a compatible installed library. NASTRAN uses a dedicated parser; Gmsh 2.2 ASCII is attempted natively with a meshio fallback for declined variants. Material extraction is requested separately.
  2. Normalize. Adapters convert native objects to canonical arrays, including volume cells when available. Native library objects can also be constructed lazily from MeshInput.
  3. Execute. A registry-created callable runs the selected operation objects one at a time. Each run() wraps execution, tracks timing, and wraps uncaught failures with the operation ID.
  4. Report. The workflow collects issues and any last_quality_metrics, then computes a summary. An uncaught operation error interrupts the workflow; it is not recorded as a partial result.

Evidence: mesh_loader.py:182–308, base.py:106–131, operation_registry.py:176–207.

The shared data contract

MeshInput

Holds vertices, surface faces, volume connectivity keyed by element type, optional cell materials and source metadata. Property access returns copies for geometry; setters invalidate cached native and adjacency data.

MeshIssue

A finding has an operation ID, category, severity, message, locations, metrics and metadata. A location identifies an element and can carry coordinates and adjacency.

QualityMetrics

Stores numerical values, distribution statistics, a threshold, violation count and provenance. Serialized output contains statistics and counts, rather than the raw values.

InspectionResult

Groups issues and metric distributions with elapsed time and severity/category counts. passed derives from the summary: no errors or critical issues.

Ownership and cache behavior

vertices, faces, volume_cells and cell_materials getters return copies; assignment through their setters clears cached native and adjacency data. However, the constructor and setters retain an input NumPy array directly. Mutating an array still held by the caller can therefore change the mesh without invoking a setter or invalidating a native cache. material_names also exposes its dictionary directly. Use new arrays on assignment and avoid modifying shared inputs after a native object has been constructed.

get_native(library) uses the adapter factory and caches up to eight native objects per mesh. A cache miss is constructed under a lock; existing entries are returned directly, and the oldest inserted entry is evicted when the limit is exceeded. The cache can be bypassed via the operation caching flag. This mechanism does not mean every operation uses the cache: surface cell quality calls adapter.from_canonical(mesh) directly.

Loading, conversion and materials

RouteBehavior and boundaries
Format dispatchThe extension-to-library list defines preference order. Unless a library is specified, the loader chooses the first available library for that extension. Availability and format listing do not guarantee that every element or feature round-trips through that library.
Native parsers.nas and .bdf use the NASTRAN parser. .msh first attempts the native Gmsh 2.2 ASCII parser; a ValueError from that parser triggers the normal library path. .fem follows the meshio route.
Adapter conversionWith the default extract_volume_cells=True, the selected adapter converts the loaded native object to MeshInput. The alternative surface-only path extracts vertices and faces and validates their shape. Direct MeshInput construction itself does not run the loader’s array validator.
MaterialsMaterial extraction is opt-in via material_array_name. For NASTRAN it requests the PSOLID mapping; for native Gmsh it requests physical-group tags; other adapter paths extract data from the native mesh. Multi-material checks need compatible volume cells and material assignments.
Saving.nas and .bdf use a native writer; other paths use an adapter, preferring meshio when available for a mapped format. The selected format and adapter affect preservation of mesh features.

The loader accepts optional allowed directories. The MCP backend’s load handler calls it without that option; the backend separately supports an optional allowlist for save paths. These are distinct controls.

Operations and extension points

Importing the package imports the operation subpackages, which register built-in instances in the shared registry. Each operation supplies metadata and an execute(mesh) implementation; the registry supports selection by ID, category, library and tag, and builds custom or full workflows.

FamilyRepresentative workWhere
Surface topologyBoundary and non-manifold elements, duplicate geometry, components, intersections and orientation.operations/topological/
Surface qualityComputes per-cell metric distributions and emits issues for threshold violations.cell_quality.py
Volume and materialsCell connectivity and closure, volume quality, boundary layers, material interfaces and per-material statistics.operations/volumetric/

Checks are not all delegated to external libraries: for example, boundary detection builds edge-to-face adjacency directly from the canonical mesh and groups boundary edges into loops. Quality checks use adapter functionality. Shared utility modules supply topology, metrics, cell type and dimensionality logic.

Selection is explicit

The workflow resolves IDs when it is created and raises ValueError for unknown IDs. It keeps the supplied order, including repeated IDs; a full workflow uses the registry’s current insertion order. Duplicate registration of an existing ID is ignored. Metadata describes recommended libraries, tags and adjacency requirements, but the workflow loop does not itself choose an adapter, precompute adjacency or filter by dimensionality. Individual operations decide how to obtain the data they need and when to return no findings.

To extend the system, implement metadata and execute(mesh) on a BaseOperation, then register an instance with registry.register(MyOperation()). Quality-producing operations populate last_quality_metrics in addition to returning issues. Although register_operation documents decorator use, its implementation registers the supplied object directly; do not assume it instantiates a decorated class.

Worked trace: boundary and cell quality

Consider a workflow created with ["topology.detect_boundary_edges", "quality.compute_cell_quality"]. The registry resolves those two instances in that order. The boundary check builds an edge-to-face map, selects edges with exactly one incident face and groups them into loops. When boundaries exist, it produces one issue with edge locations and a severity derived from the boundary-edge ratio. An open surface may be intentional, so the code’s severity reflects its own heuristic rather than a universal validity rule.

The quality check selects an adapter, converts the mesh and computes each configured metric. For successful nonempty metrics it filters VTK’s -1 undefined sentinel, evaluates the metric-specific threshold direction, and records a distribution even when there are zero violations. It emits issue records for violations. The workflow appends both channels and computes its summary; summary counts are counts of issue records, not counts of defective edges or cells.

For volume quality, some higher-order elements are evaluated on corner-linearized cells, and the metric metadata records that provenance. The separate midside-deviation metric measures quadratic geometry and is tagged accordingly. Volume-quality issue locations are capped at 100 before the general serialization limit is applied.

Evidence: boundary_edges.py:54–119, cell_quality.py:80–155, 157–221, volume_cell_quality.py:200–260, 300–352, models.py:191–211. The quality metric tests:77–144 exercise metric collection, including zero-violation metrics.

Interfaces and state

Python API. A caller can construct a mesh directly or load one, select a workflow through registry, and inspect the returned object. Adapter factories expose five named integrations: trimesh, PyVista, PyMeshLab, meshio and vedo; actual availability and capability depend on installed libraries.

from mesh_issue_examiner import registry
from mesh_issue_examiner.utils import load_mesh_from_file

mesh = load_mesh_from_file("model.stl")
result = registry.create_full_workflow()(mesh)
print(result.summary, result.passed)

MCP interface. The server maintains in-memory mesh and result dictionaries keyed by mesh ID. Load stores a mesh; inspect selects operations or categories, runs the workflow and caches the result; issue and quality tools provide detail. The inspection response itself returns a summary. FastMCP wraps this backend and exposes tools and resources.

MCP lifecycle and detail

ActionBehavior
mesh_loadStores a mesh under its ID and returns basic metadata. An ID defaults to the file stem. Loading a second mesh under the same ID replaces the mesh entry but does not clear the prior result entry; inspect again or clear the cache to avoid retrieving the old result.
mesh_inspectAccepts either categories or operation IDs, not both. Omitting both runs the full registry; explicit IDs are validated. On success it overwrites the cached result and returns summary, pass flag and time.
mesh_get_issuesFilters by exact severity and category, then paginates issue records with a default limit of 50 and maximum of 200. Each record uses the ordinary location-limited serializer.
mesh_get_quality_metricsOptionally filters by metric name and serializes statistics, threshold and counts, not the underlying array.
mesh_clear_cache / mesh_saveClear removes one or all cached meshes and results. Save writes the cached mesh using its output extension; save registration differs between the backend’s default tool list and the FastMCP wrapper.

FastMCP also exposes an operations catalog, mesh information and inspection summary as resources. Both server caches are process-local, and result retrieval requires a successful prior inspection.

Reading results correctly

  • A pass is not proof every metric ran. Surface quality catches individual metric errors and logs a warning before continuing; conversion errors can also skip that check. A result can lack a metric without recording a corresponding issue.
  • Serialized detail is reduced. MeshIssue.to_dict() includes only the first ten locations and the number stored in that issue. Some operations cap locations before serialization, so this count need not equal the total number of affected elements. Metric serialization omits raw values. MCP detail endpoints use these same serializers; Python callers can inspect the stored in-memory locations and metric values.
  • Configuration and concurrency deserve care. The workflow passes a config to run(), but the wrapper uses it for the mesh caching flag while operations such as cell quality read self.config. The sequential workflow shares registered instances and their mutable last_quality_metrics; concurrent runs should not be assumed isolated.
  • Summary is conditional. With combine_results=False, the workflow skips compute_summary(); passed reads absent summary flags as false and can therefore report true even when issues are present. Compute the summary before interpreting that property.
  • Parallel setting. OperationConfig.parallel_enabled exists, but the inspected registry workflow executes a normal sequential loop and does not consult it.
  • State is process-local. MCP caches are dictionaries, while each mesh caches native conversions with a per-instance limit. These are convenience caches, not durable storage.

Geometry representation is deliberately portable, but library-specific conversion and supported element types affect which computations can run. Dimensionality detection is available as a utility; the registry loop itself does not automatically filter operations by dimensionality.

It samples representative surface, volumetric, material and quality operations and reads relevant tests rather than auditing every algorithm, running the test suite or benchmarking runtime.
